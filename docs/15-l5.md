## 1. 效能怎麼測？不用秒數

「效能」這一節最大的技術障礙是：**牆上時鐘在共用機器上不可重現**。
同一份程式碼在 CI 與筆電上可能差三倍，斷言「必須小於 50ms」等於製造 flaky 測試。

所以改用**操作次數**：

```cpp
struct Counted {
  int v;
  static long long ops;
  friend bool operator<(const Counted& a, const Counted& b) { ++ops; return a.v < b.v; }
  // ...
};
```

把 `Counted` 丟進待測函式，跑完看 `ops`。這是演算法的性質，與機器無關。

實測（L5.01 起始碼）：

| 測試 | 結果 |
|---|---|
| `count_duplicates` 的 O(n²) | `Counted::ops <= limit` 不成立（n=1000：約 500k 次 vs 上限 200k） |
| `top_two` 的「先排序」 | `Counted::ops <= limit` 不成立（n=2000：約 22k 次 vs 上限 12k） |

而且 `top_two` 還有一個**正確性**錯誤：`{5,5}` 會回傳 `{5,5}`，但介面要求 `nullopt`
（次大必須嚴格小於最大）。這一個測試同時抓到語意與成本兩個層面。

## 2. 併發：讓「錯誤只在某些排程出現」變得可測

L5.02 的三個錯刻意選成**確定性可測**：

| 錯 | 怎麼被抓到 |
|---|---|
| `parallel_sum` 忽略 `n % k` 的餘數 | 單元測試（`parallel_sum({1..10}, 3)` 得到 45，期望 55） |
| `parallel_fill` 每段少填最後一個 | 單元測試（`out[i] == i*2` 在段尾失敗） |
| `parallel_count` 用一般 `int` 累加 | **靜態規則**（見下） |

### 為什麼需要「必須寫法」的規則

第三個錯是**資料競爭**。但實際跑起來：

```
parallel_count：偶數個數（1..10 有 5 個）   [  ok  ]   ← 通過了！
```

競爭沒有顯現。這不是意外，而是資料競爭的本質 —— 它只在特定排程下出錯。
如果只靠測試，這個 bug 會永遠躲在綠色裡。

所以我擴充了 `static_rules` grader，加入 `required: true` 的規則：

```json
{ "id": "atomic-counter", "pattern": "std::atomic", "required": true,
  "message": "共享計數器必須用 std::atomic（多執行緒同時 ++ 是資料競爭）" }
```

現在起始碼會拿到：

```
static_rules  fail  發現 1 處違規
  · [atomic-counter] 共享計數器必須用 std::atomic
```

**這個設計本身就在教課**：不能只靠測試，因為有些錯誤不會在測試中出現。
這也是為什麼真實專案需要 TSan（本環境沒有，見 POC 報告 §3）。

## 5. 下一步：L6（職場整合）

| 順序 | 節點 | 說明 |
|---|---|---|
| 1 | **L6.01 讀陌生程式碼** | 給一份「別人的」多檔案專案（用 `support` 檔），修一個真實 bug |
| 2 | **L6.02 交付與審查** | code review 清單、重構、把三個需求整合成一個可運行的程式 |

L6 的設計難點：**「讀陌生程式碼」無法只用單一題目驗證**。
現在想到的做法是用 `support/` 放一個「同事寫的」模組（含介面與實作），
學員只能透過介面理解它，然後修一個跨檔案的 bug。這比單檔題目更接近真實。
