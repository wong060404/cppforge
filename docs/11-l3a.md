# L3 · 第一切片：std::map（L3.01）

> 版本 v0.1 · 接續 `10-m2d.md`
> 目標：進入 L3（泛型與標準庫）。第一個容器不是 `vector`（L1 已用過），而是 `map` —— 因為它同時帶出「有序容器、迭代器、`operator[]` 陷阱」。

---

## 1. 先驗證上一輪：一個我宣稱但從未實測的事

L2.06 的課文說「基底類別少了 virtual 解構函式會洩漏」，而且我在更早的輪次還說過
「這剛好能被洩漏檢查抓到」。但我**從來沒有實際跑過**。

這一輪補上：寫一對只差 `virtual` 的程式，各自跑一次洩漏檢查。

| 版本 | 結果 |
|---|---|
| `struct Base { ~Base() = default; ... }` | `exit=86`，**`LEAKCHECK: 1 leaked block(s), 400 bytes`** |
| `struct Base { virtual ~Base() = default; ... }` | `exit=0`，`LEAKCHECK: clean (0 leaked blocks)` |

兩個版本只差一個 `virtual`，結果一個洩漏、一個乾淨。**教學宣稱現在有實驗支撐**，
而且證明我們的洩漏檢查確實能抓「解構函式沒被呼叫」這個抽象的失敗模式（不只是「忘了 delete」）。

## 2. 新增的節點：L3.01 std::map

| 項目 | 內容 |
|---|---|
| 要實作 | `count_of`、`bump`、`keys_in_order`、`most_common` |
| 要修的錯 | ① `count_of` 用 `m.count()`（只給 0/1） ② `bump` 用 `insert`（不累加） ③ `keys_in_order` 收集 value 而非 key |
| 刻意正確 | `most_common`（示範「利用 map 的排序省一次比較」） |

### 為什麼是這三個錯

這三個錯剛好覆蓋 **`std::map` 的三個 API 語意誤解**，而且都不會被編譯器抓到：

| 錯 | 以為的語意 | 實際語意 |
|---|---|---|
| `m.count(k)` | 出現次數 | 0 或 1（key 唯一） |
| `m.insert({k,1})` | 設成 1 / 累加 | **只在不存在時**加入 |
| 走訪 `[key, value]` | 拿哪個都一樣 | 要 key 就用 `key`（很明顯，但因為結構化綁定把兩個名字都給了，反而容易拿錯） |

`most_common` 保留正確，是為了呈現「map 走訪已排序」這件事 —— 它用嚴格大於 `>` 就自動
做到「並列取字典序最小」，這是本節最優雅的一行。

## 3. 順手補了一個基礎設施：`CF_EXPECT_EQ_RANGE`

`std::vector` 沒有 `operator<<`，所以原本 `CF_EXPECT_EQ(v1, v2)` 失敗時只能說「不相等」。
這一節的 `keys_in_order` 正是回傳 `vector<string>`，訊息會一無所用。

**不能**替 `std::vector` 加 `operator<<`（那要放進 `namespace std`，是未定義行為），
所以改用專門的巨集：把容器攤開成 `[a, b, c]`。

實際效果（L3.01 起始碼）：

```
keys_in_order(m) == (…)（實際 [2, 5, 0]，期望 [a, b, c]）
keys_in_order(m) == (…)（實際 [2, 3, 1]，期望 [apple, mango, zebra]）
```

第二行特別有教學價值：`[2, 3, 1]` 是「依 key 排序後的值」——
學員看到這個陣列，就同時理解了「我收集錯欄位」與「map 是排序的」兩件事。
