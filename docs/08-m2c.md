## 1. 先驗證上一輪：double free 偵測真的能安全回報

上一輪把洩漏檢查改成「未登記的指標不呼叫 `free()`」。這一輪用 L2.04 的參考解製造一個真的淺拷貝：

```cpp
// 把深拷貝改成
IntArray::IntArray(const IntArray& other)
    : data_(other.data_), size_(other.size_) {}   // 只抄指標
```

結果：

| grader | 結果 |
|---|---|
| compile | pass |
| unit_test | `執行期崩潰（0xC0000374）—— 常見於越界寫入、重複釋放（double free）或空指標` |
| runtime_safety | **`重複釋放（double free）2 次`**，程式**沒有崩潰**，測試完整跑完 |

兩個重點：

1. **偵測層不再自殺**。改之前，`free()` 一塊已釋放的記憶體會讓工具自己崩掉，學員只會看到「可能崩潰」。現在它記錄、跳過、繼續跑。
2. **0xC0000374 是 `STATUS_HEAP_CORRUPTION`** —— 這正是 double free 的典型死法，所以 `unit_test` 的訊息也順便升級了：不再只說「可能崩潰」，而是給出退出碼與三個最可能的原因。

## 2. 新增的節點：L2.05 運算子重載

| 項目 | 內容 |
|---|---|
| 型別 | `Vec2`（二維整數向量） |
| 要實作 | `+=`、`==`、`length()`、自由函式 `operator<<` |
| 要修的錯 | ① `+=` 只加 x 軸 ② `==` 只比 x 軸 ③ `<<` 的格式少了括號與逗號 |

### 三個教學決定

**（a）`length()` 故意是對的。**
課文最後直接寫明「不是每個函式都一定有錯」。真實程式碼就是這樣 —— 你的工作是定位「哪幾個有問題」，不是全部重寫。這也讓「逐個驗證」變成必要動作，而不是「看到什麼就改什麼」。

**（b）`operator<<` 用 `std::ostringstream` 精確驗證格式。**
輸出格式不是「好看的東西」，是**介面的一部分**。測試斷言 `os.str() == "(1, 2)"`，所以 `1 2`、`(1,2)`、`(1, 2 )` 全都會被擋下來。

**（c）`+=` 的測試檢查「回傳的是不是 `*this`」。**
```cpp
Vec2& r = (a += b);
CF_EXPECT(&r == &a);        // 位址相等才算真的回傳自己
```
這比「值正確」更嚴格：回傳一個內容相同的新物件也會通過值檢查，但鏈式運算會失效。

## 3. 為什麼這節對後面「有複利」

現在所有節點的測試失敗訊息都還是這種：

```
[FAIL] 兩軸都要更新
       tests.cpp:14  期望 a.y() == 6 但兩者不相等
```

訊息只能告訴你「哪一行、哪個條件」，看不到實際值。而 `operator<<` 是唯一能讓型別自己決定「我該怎麼被印出來」的機制 ——
一旦型別有了 `<<`，後續就能做：

- 測試框架在失敗時印出實際值（`CF_EXPECT_EQ` 的進階版）
- 節點的除錯輸出直接 `std::cout << v`
- 錯誤訊息變成 `(1, 2) + (3, 4) = (4, 6)` 這種一眼看得懂的形式

本輪先把 `<<` 教會，**下一輪再把測試框架接上去**（`cf_test.hpp` 目前只印條件字串，還沒有利用 `<<`）。這是刻意分期：先把能力做出來，再讓它產生價值。
