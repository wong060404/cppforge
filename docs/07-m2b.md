「洩漏偵測獨立於單元測試」。

做法：拿 L2.02 的起始碼，**只修邊界檢查、故意保留洩漏**，然後完整評測。

B 這一列就是證據：**測試全過，但工具仍然抓到洩漏**。兩者是獨立的檢查，
所以「我測試都過了」不等於「我的程式沒有資源問題」。

## 2. 新增的節點：L2.04 複製語意

| 項目 | 內容 |
|---|---|
| 主題 | 深拷貝 / 淺拷貝、rule of three、自我賦值安全 |
| 類別 | `IntArray`（持有 `int*`，**可以複製** —— 與 L2.02/L2.03 的所有權語意相反） |
| 要修的錯 | ① 複製建構子配置了記憶體但沒複製內容 ② 複製賦值覆蓋指標前沒釋放舊資料 |

刻意設計的教學點：

- **錯誤 ① 不會崩潰、不會漏記憶體**，只是內容變成 0 —— 只有測試會發現。
- **錯誤 ② 不會讓任何測試失敗**，只有洩漏檢查會發現。

兩個錯分別由兩種機制抓到，正好示範「為什麼需要多種 grader」。

### 為什麼 L2.02 叫 `= delete`，L2.04 卻要實作？

這是**語意**問題，不是「哪個高級」：

- `Buffer` 代表「一塊我獨佔的緩衝區」→ 複製沒有意義 → `= delete`（或 `unique_ptr`）。
- `IntArray` 代表「一組值」→ 複製一份很合理 → 實作深拷貝。

課程要傳達的是：**先問「這個東西被複製時應該發生什麼」，再決定寫哪一種**。

## 3. 為了這個節點，先升級了洩漏檢查

淺拷貝的典型後果是 **double free**。但先前的洩漏檢查遇到未登記的指標時會
「印一行訊息，然後照樣 `free()`」—— 那本身就是未定義行為，會讓測試程式直接崩潰，
學員只會看到「測試程式沒有產出結果（可能崩潰）」，看不到原因。

改法（`lib/leak_check.cpp`）：

```cpp
void release(void* p) noexcept {
  const bool tracked = is_tracked(p);
  record_free(p);          // 若未登記 → 記錄一次 double free
  if (tracked) std::free(p);   // 未登記就不 free，避免 UB
}
```

- 同一塊記憶體被釋放兩次 → 計數 + 印 `LEAKCHECK: double free of 0x… (ignored)`，
  程式**繼續跑完**，測試結果仍然完整。
- 結束時只要有洩漏或 double free → `_Exit(86)`，評測器判失敗。
- `grading.mjs` 的 `runtime_safety` 現在分開回報：`重複釋放（double free）N 次`
  vs `記憶體洩漏 N 塊`。

錯誤圖鑑也補了對應條目（第 **22** 條：重複釋放），並加進圖鑑自檢的真實訊息清單。

## 4. 內容 CI 的一個自我修正

上一輪我加了 `bugCount` 檢查：「起始碼必須讓 ≥N 個測試失敗」。
這一輪 L2.04 立刻被它判失敗：

```
⚠ 宣稱 2 個錯，實際讓 1 個測試失敗
```

但課文沒有說謊 —— 第二個錯（賦值洩漏）**在設計上就不會讓測試失敗**。
問題出在檢查方法：它假設所有缺陷都會反映在測試上。

修正：把「訊號」定義成

```
訊號 = 失敗的單元測試數 + (記憶體檢查失敗 ? 1 : 0)
```

L2.04 現在顯示：`訊號 = 1 個失敗測試 + 記憶體檢查失敗 = 2` —— 與宣稱一致，
而且**訊息本身就說明了「兩個錯由兩種機制各自抓到」**。

> 這個小事件值得記錄：檢查機制也會有盲點，而它最好的用途就是
> 逼迫作者把「宣稱」寫成「可測量的事實」。
