## 1. L6.01 讀陌生程式碼

前 28 節的介面都是「為你設計的」。這一節第一次給你**別人的模組**：

```
stats.hpp / stats.cpp     ← 「同事寫好的」統計模組
format.hpp / format.cpp   ← 「同事寫好的」格式化模組
```

兩者都不可修改，只能讀懂再使用。三個陷阱：

| 陷阱 | 實情 |
|---|---|
| `Summary::mean` 看起來是普通平均 | 它**只算非零元素**（0 代表感測器沒讀到值） |
| `compute()` 回傳 `std::optional` | 空輸入回 `nullopt`，直接 `.value()` 會丟 `bad_optional_access` |
| 輸出格式 | `mean` 要兩位小數、`percent()` 自帶一位小數與 `%` —— 這些**都不在型別裡** |

最能說明問題的測試是這一個：

```cpp
// 全體平均 = 18/4 = 4.5；模組的非零平均 = 18/3 = 6.0
// 用 6.0 → 只有 7 超過 → 25.0%；用 4.5 → 三個都超過 → 75.0%
const std::vector<int> v{0, 5, 6, 7};
CF_EXPECT_EQ(above_average_line(v), std::string("above=25.0%"));
```

起始碼自己重算了全體平均 → 得到 75.0%。**這不是算錯，是沒讀懂。**

## 2. L6.02 交付完整程式

第一個 `io_match`（而不是 `unit_test`）的節點：程式從 stdin 讀資料，輸出排序報表，
評測**逐字比對 stdout**。

三個坑都是真實工作的坑：

| 坑 | 為什麼真實 |
|---|---|
| 同名要合併 | 需要「分組聚合」：`map` 的 `operator[]` 插入語意，在這裡**正好是解法**（與 L3.01 的陷阱是同一個特性） |
| tie-break 寫在比較函式裡 | 不能排兩次（第二次會覆蓋第一次），不能用 `>=`（違反嚴格弱序會崩潰） |
| 金額不能用 `int` | `100000 × 100000 = 10¹⁰` 超出 `int` → **有號溢位是 UB**（L4.02 的回馬槍） |

測試資料刻意包含一組 `100000 × 100000` 與一組同金額不同名稱，讓這兩個坑一定會踩到。

## 3. 這一輪補的兩個引擎修正

**（1）`io_match` 的期望輸出不見了。** 評測器讀 `cs.expect`，我的節點寫成 `cs.stdout`，
結果四組測資全部「預期「」」。修法：兩種都接受，並在內容 lint 加上
「`io.cases[i]` 缺少 `expect`/`stdout`」的檢查 —— 否則這個錯誤只會在跑測試時才發現。

**（2）`bugCount` 不支援純 `io_match` 節點。** 原本只讀 `unit_test` 的失敗數，
L6.02 沒有單元測試 → 訊號永遠 0。修法：`io_match` 也輸出 `metrics.failed`（每組測資算一個訊號）。
